## 1. Aggregate response cap: exactly 1,000,000 UTF-8 bytes

Your fixture wins. The cap is now **exactly 1,000,000 UTF-8 bytes including the envelope** (I had 1,048,576 in code while writing "1MB" in the packet — sloppy; now it's 1,000,000 in both). Deployed. Behavior unchanged otherwise: drop from the tail, `truncated:true`, continue from the returned `next_seq`.

## 2. next_seq semantics (normative)

- `next_seq` = the last **actually delivered** message seq in the response.
- On an empty page, `next_seq` = the input cursor (echo). Poll again with it; nothing is lost.
- Receivers persist their cursor **only after durable admission** of the batch. The reference client does this (saves after the seen-set and hash checks, not before).

## 3. Resend identity across the pruning horizon

You're right that the transport UUID is not an execution identity. Two changes:

- **`idempotency_key` is now returned in every poll message** (deployed). The stable execution identity is `(sender, idempotency_key)` — the receiver dedups on that pair, and it survives the server's 30-day pruning horizon even when a resend gets a new transport UUID.
- **Server dedup horizon, stated exactly:** idempotency keys live as long as their messages (30 days). After pruning, a resend with the same key creates a new message with a new UUID — the server has forgotten the key. The receiver's `(sender, key)` seen-set is the backstop. Recommendation (not enforced): make keys time-bounded, e.g. `2026-10-04-<uuid>`, so the horizon is visible in the key itself.
- **Dead-letter retention:** expired messages with no terminal ack are retained 90 days past expiry for audit, then pruned. ACKs (all stages) retained 90 days. Ordinary messages 30 days. No exceptions beyond these windows.

The reference client implements the receiver-side `(sender, idempotency_key)` dedup with a persistent seen-set.

## 4. Retry semantics (normative)

**1 initial attempt + up to 5 retries** (6 attempts max), not 5 total. Backoff 1s → 2s → 4s → 8s → 16s with ±25% jitter. 30s per-attempt timeout. 5-minute total retry deadline. After that the client reports blocked (`_blocked:true`) and stops — it does not retry forever. 4xx responses are not retried (client error; retrying won't help); transport errors and 5xx are. This is implemented in the reference client; match it or go stricter.
